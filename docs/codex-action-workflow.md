# Codex 액션 실행 구조

## 실행 원칙

- Codex는 사용자 요청과 대화 문맥을 해석하고 다음 액션 또는 최종 편집 명령을 JSON으로 반환한다.
- Codex thread는 프로젝트와 분리된 임시 작업 디렉터리에서 `read-only`로 실행한다.
- 파일, SQLite, 편집 문서는 앱 코드만 변경한다.
- JEV 선행 라우팅은 사용하지 않는다. 일반 요청은 Codex 한 번으로 답변하거나 편집한다.
- 추가 정보가 필요한 경우에만 앱이 조회 액션을 실행하고 결과를 같은 Codex thread에 돌려준다.

## 응답 상태

| 상태 | 의미 | 앱 동작 |
| --- | --- | --- |
| `actions` | 이미지 검색이나 원본 확인 결과가 필요함 | 조회 액션 실행 후 결과 전달 |
| `complete` | 답변, 제안 또는 편집 명령이 완성됨 | 검증 후 저장 |
| `ask_user` | 사용자만 제공할 수 있는 정보가 필요함 | 질문을 기록하고 현재 실행 종료 |

`actions`에는 읽기 액션만 포함한다. 문서 명령과 제안은 `complete`에서만 제출한다.
같은 조회가 다시 요청되면 기존 결과를 재사용한다. 새 조회가 하나도 없는 반복 응답은 진행 없음으로 종료한다.
호출 횟수만으로 정상 작업을 중단하지 않는다.

## 현재 조회 API

- `search_assets`: SQLite의 이미지 이름과 설명을 검색한다. BLOB은 읽지 않고 결과 수를 제한한다.
- `inspect_assets`: 이미 검색했거나 작업에 연결된 이미지 ID만 최대 4개 읽어 Codex에 전달한다.

이미지 생성은 제공자가 연결될 때 별도 액션으로 추가한다. 현재 계약에는 노출하지 않는다.

## 문서 변경

Codex는 `EditorCommand[]`를 반환하고 앱이 다음 순서로 처리한다.

1. Structured Output 스키마 검사
2. 새 Element, Placement, Slide ID를 앱 발급 ID로 치환
3. 선택 Element와 장 범위 검사
4. 실제 슬라이드, Element, Placement, 이미지 asset ID 검사
5. 문서 복제본에 전체 명령 적용
6. 문서 불변 조건 검사
7. revision 확인 후 한 번의 변경과 undo 이력으로 저장

한 명령이라도 실패하면 실제 문서와 undo 이력은 바뀌지 않는다. 이미지 삽입은 조회하거나 업로드한 asset ID만 허용한다.

## 제안 수명

- 주제와 훅 후보는 문서 명령과 별도로 저장한다.
- 후보 클릭은 선택이며 즉시 문서를 바꾸지 않는다.
- 선택한 후보를 포함해 다음 메시지를 보내면 Codex가 수정 또는 적용 의도를 대화 문맥에서 판단한다.
- 수정 결과는 새 제안 세트로 저장하고 이전 카드는 비활성화한다.
- 새 메시지를 보낸 뒤에는 선택하지 않은 이전 카드도 비활성화한다.

## 진행 표시

기존 ContentJob SSE에 실제 실행 단계를 기록한다. 기본 단계는 요청 이해와 작업 계획, 조회 액션, 결과 확인과 다음 작업 계획, 편집 명령 검증, 문서 적용이다. 실행 콜백으로만 상태를 바꾸며 추정 진행률은 표시하지 않는다.

## 비용과 병렬성

- 최초 Codex 호출에만 문서와 대화 문맥을 보낸다.
- 후속 호출에는 새 액션 결과만 전달하고 같은 thread의 문맥을 재사용한다.
- 문서 전체 대신 변경 명령만 반환한다.
- 여러 검색어는 한 액션에 묶는다.
- 독립된 이미지 파일 읽기는 병렬로 처리한다.
- 같은 문서의 최종 변경은 revision 충돌을 막기 위해 직렬·원자적으로 처리한다.
