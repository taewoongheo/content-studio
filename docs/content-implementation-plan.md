# 콘텐츠 생산 시스템 구현 계획

작업 브랜치: `feat/content-production-pipeline`

## 1. 이번 구현의 결과

사용자가 제작 개수를 입력하고 시작하면 성과를 한 번 갱신한 뒤 콘텐츠별 분석·제작을 병렬 실행한다. 실행 화면에서 단계별 진행과 저장 내용을 확인하고, 완성한 포스트를 편집기로 연다. 외부에서 수정·업로드한 후 URL을 등록하면 게시 정보와 이미지를 보존한다.

구현 순서는 저장 계약 → 자료 조회 → 단계 실행 → 실행 화면 → 통합 검증 → 현재 DB 변환이다.

## 2. 확정한 운영 규칙

- 게시 콘텐츠의 중복 검사는 현재 시각부터 최근 24시간에 실제 게시된 콘텐츠를 대상으로 한다. ‘최근 1일’은 이 기준으로 구현한다. 진행 중·중단·실패·검토 대기 초안은 기간과 관계없이 비교한다.
- 소재와 유형이 함께 겹치면 먼저 저장된 실제 초안을 유지하고 나중 작업이 변경한다.
- 중복 충돌로 바꾸는 경우 분석 draft와 로그의 제작 방향을 현재 선택으로 갱신한다. 이전 선택과 변경 이유를 별도 이력으로 남기지 않는다. 기존 초안을 그대로 유지한 채 메타데이터만 바꾸지 않고 실제 제작 내용도 맞춘다.
- 추가 조사로 방향이나 내용을 바꾼 경우 기존 판단과 변경 내용·이유를 보존한다.
- 중단은 재개할 수 있도록 draft를 보존한다. 사용자가 명시적으로 취소·제거하면 실행을 종료하고 상위·분석·제작 draft를 모두 삭제한다.
- 취소 처리 중 쓰기를 차단하고, 뒤늦은 CLI 응답이 삭제된 draft를 다시 생성하지 못하게 한다. 저장된 프로젝트 삭제는 별도 기존 프로젝트 삭제 기능으로 처리한다. draft가 없는 미게시 작업은 중복 대상을 점유하지 않는다.
- 외부 피드백 저장 기능은 제공하지 않는다. 사용자가 직접 수정하며, 수정 이유를 자동 추정하지 않는다.

## 3. 데이터·API

합의한 신규 7개 테이블을 구현한다. 컬럼 기준은 [테이블 설계](content-data.html)를 따른다.

| 소유 단위 | 책임 |
| --- | --- |
| 작업 전체 draft | 현재 단계·전체 상태·로그 연결 |
| 분석 draft | 조사·분석·제작 방향·한 일·남은 일 |
| 제작 draft | 추가 조사·내용 작성·검토·한 일·남은 일 |
| 제작 로그 | 확정한 판단·실제 결과·사용 자료·최신 성과 |
| 선별 레퍼런스 | 사용자가 보관한 사례와 참고할 부분 |
| 이미지 묶음·슬라이드 | 외부 자료·실제 게시 모습의 전체 축소본 |

분석은 TEXT, 방향과 성과는 개별 컬럼, 반복되는 자료·장별 내용은 검증한 JSON으로 저장한다. 실제 문서와 사용 자산은 기존 프로젝트 저장소를 사용한다.

읽기·중간 저장·단계 완료·중단·재개·취소·URL 등록 API를 만든다. 상태 전환과 관련 저장은 트랜잭션으로 처리한다. 일반 저장 API는 존재하는 작업만 수정하며, 새로운 draft 생성은 시작 API에서만 한다.

로그 조회에서 미완성·게시 완료·기존 자료를 구분한다. 제작 전 판단과 실제 제작 내용을 구분해 보여준다. 기존 게시글의 부족한 정보는 웹의 정보 편집 화면에서 사용자가 채울 수 있게 한다. 수동 입력은 시스템이 자동 분석했다는 기록으로 표시하지 않는다.

## 4. 자료 조회와 제작 도구

- Apify 키는 서버 설정에서 읽는다. 키를 브라우저나 CLI 프롬프트에 전달하지 않는다.
- 실제 슬라이드쇼 URL로 지표·게시 시각·전체 이미지 반환을 먼저 검증한다.
- 시작 요청에서 오늘부터 3일 전까지의 등록 게시물 성과를 한 번 갱신한다. 제공하지 않는 수치는 NULL로 두고 실패 시 이전 값을 보존한다.
- URL 등록 시 첫 성과도 제공되는 범위에서 저장한다. 게시 시각·전 장 이미지 저장 성공을 완료 조건으로 삼는다.
- 과거 로그·선별 레퍼런스·진행 중 초안을 검색하고, 자체 미리보기 또는 외부 축소 이미지를 읽을 수 있게 한다. 각 단계에서 필요할 때 조회하며 최소 조회 개수는 강제하지 않는다.
- 템플릿 없이 새 프로젝트를 만드는 API/MCP 경로를 추가한다. 공통 시각 규칙은 한 곳에서 관리하며 제작 지침과 연결한다.
- 기존 미리보기·편집·저장·포스트 열기를 재사용한다. 제작 완료 전에 모든 장을 검토하고 저장 상태를 확인한다.

## 5. 로컬 CLI 실행

콘텐츠 하나를 하나의 논리적 작업으로 관리하고, 단계별 `codex exec` 호출은 서버가 순서대로 실행한다. 서로 다른 콘텐츠는 분석부터 병렬로 진행한다.

1. 분석 실행은 분석 draft를 중간 저장하고 구조화된 완료 출력을 반환한다.
2. 서버가 필수 출력·저장 성공을 확인하고 분석 단계를 완료한다.
3. 제작 실행은 확정한 방향과 자신의 draft를 읽고 제작한다.
4. 서버가 프로젝트·검토 결과·로그 저장을 확인한 뒤 제작을 종료한다.

단계별로 사용할 저장 명령과 완료 명령을 구분하고, API가 현재 단계와 작업 ID를 검사한다. 프롬프트만으로 단계 순서를 강제하지 않는다. CLI 이벤트는 실행 관측에 사용하고 DB 저장 성공과 구분한다.

현재 설치된 CLI와 로그인 환경을 사용한다. 모델을 임의로 변경하지 않는다. 중단은 프로세스를 종료하되 마지막 저장을 유지하고, 재개는 현재 단계의 draft와 이전 단계의 확정 출력으로 새 실행을 시작한다. 앱 재시작 후 진행 중 상태는 중단으로 정리한다.

## 6. n8n 형태의 실행 화면

React Flow로 확대·이동 가능한 고정 파이프라인을 구성한다. 상단에 시작 버튼과 제작 개수를 두고, 공통 수집 노드에서 콘텐츠별 흐름으로 분기한다.

```text
시작 → 공통 성과 갱신
              ├─ A: 분석·방향 → 콘텐츠 제작 → 포스트 열기
              ├─ B: 분석·방향 → 콘텐츠 제작 → 포스트 열기
              └─ C: 분석·방향 → 콘텐츠 제작 → 포스트 열기
```

- 인스턴스마다 안정적으로 유지되는 색상을 노드 테두리와 연결선에 적용한다. 색 외에도 이름·아이콘·상태를 표시한다.
- 노드를 누르면 상세 패널에 해당 단계 draft를 펼친다. 조사 자료·발견한 내용·분석 또는 작성 내용·한 일·남은 일·오류·마지막 저장 시각을 읽을 수 있다.
- 저장·수정이 DB에 반영된 직후 서버가 이벤트를 보낸다. 해당 노드와 열린 상세 패널이 갱신되고 노드가 짧게 `scale(1) → scale(1.03) → scale(1)`로 박동한다.
- 단순 조회에는 박동하지 않는다. 연속 쓰기는 짧게 묶고, 움직임 감소 설정에서는 강조색·저장 시각으로 대체한다.
- 실행 중 연결선 흐름과 저장 박동을 구분한다. 화면에 없는 추정 진행률을 만들지 않는다.
- 서버 이벤트 스트림(SSE)과 초기 상태 조회를 사용한다. 재연결 시 DB를 다시 읽고 과거 이벤트를 새 저장처럼 재생하지 않는다.
- 작업별 중단·재개·취소·제거와 포스트 열기를 연결한다. URL 등록은 별도 액션으로 둔다.

## 7. 코드 소유권

| 위치 | 책임 |
| --- | --- |
| `src/domains/content-production` | 단계 실행·draft·로그·레퍼런스·게시 연결·상태 이벤트 |
| `src/domains/research` | Apify 수집과 외부 자료 조회 |
| `src/domains/slideshow` | 템플릿 없는 생성·편집·프로젝트 저장·미리보기 |
| `src/screens/content-production` | 노드 화면·단계 상세 패널·시작 및 제어 UI |
| `src/lib/mcp`와 API 라우트 | 입력 검증·명령 연결·결과 변환 |

새 도메인의 저장·실행·조회 책임은 하위 폴더로 나눈다. DB 연결 모듈은 스키마 등록만 담당한다. 기존 아키텍처 검사를 확장해 소유권을 유지한다.

## 8. 현재 DB 일회성 변환

현재 읽기 확인 결과: 스키마 v13, 프로젝트 24개, 프로젝트 자산 266개, 템플릿 5개. 프로젝트 24개 모두 주제·메시지가 있고, published_at이 채워진 프로젝트는 없다. 실제 변환 직전에 다시 확인한다.

1. 새 구현을 별도 검증 DB에서 확인한다.
2. 실행 중인 앱을 종료하고 현재 DB를 일관된 상태로 백업한다.
3. 임시 일회성 변환 도구로 새 테이블을 생성하고 각 기존 게시글에 로그를 연결한다.
4. 프로젝트 ID·주제·메시지·현재 문서에서 직접 읽을 수 있는 내용만 옮긴다. 문서·자산은 기존 저장소에 유지한다.
5. 과거 분석·선택 이유·기대 반응·성과·실제 게시 시각은 생성하거나 추정하지 않고 비워둔다. 기존 자료에 완료한 에이전트 실행이나 가짜 draft를 만들지 않는다.
6. 템플릿 5개를 자동으로 선별 레퍼런스로 바꾸지 않는다. 기존 자료로 유지한다.
7. 프로젝트·자산 수, 문서와 이미지 바이트, 외래키 무결성, 실제 열기·미리보기를 확인하고 새 앱을 실행한다.

자동 마이그레이션 프레임워크나 상시 변환 경로는 추가하지 않는다. 일회성 도구는 시스템 임시 폴더에서 사용하고 완료 후 정리한다. 부족한 정보는 사용자가 정보 편집 화면에서 채운다.

## 9. 검증과 완료 기준

- 하나의 시작 요청에서 성과 수집은 한 번, 분석은 여러 작업에서 병렬 실행된다.
- 분석 출력이 저장되지 않으면 제작이 시작되지 않는다. 중단·재개 시 현재 단계와 프로젝트를 유지한다.
- 최근 24시간 게시물과 보존된 활성 초안의 중복 조정이 작동한다. 충돌 변경은 덮어쓰고 추가 조사 변경은 이유를 남긴다.
- 취소·제거하면 모든 draft가 삭제되며, 늦게 도착한 쓰기가 복구시키지 못한다.
- 저장 이벤트가 해당 색상의 노드와 상세 패널에 반영되고 포스트 열기가 기존 편집기로 연결된다.
- 수집 실패·부분 이미지 실패·URL 재시도에서 잘못된 완료나 중복 자료가 생기지 않는다.
- 일회성 변환 후 기존 게시글과 이미지가 보존되고 빈 정보를 직접 수정할 수 있다.
- 도메인·API·실행 제어 테스트, MCP 통합 검사, 격리된 빌드와 브라우저 실동작을 확인한다.

실제 Apify 검증에는 API 키가 필요하다. 키가 준비되지 않은 경우 나머지 구현과 오류 경로 검증은 진행하되 실제 수집 성공으로 보고하지 않는다.
