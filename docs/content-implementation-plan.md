# 콘텐츠 생산 시스템 구현

작업 브랜치: `feat/content-production-pipeline`

운영 기준은 [시스템 설명](content-system.html), 테이블별 책임은 [데이터 설계](content-data.html), 게시용 슬라이드 기준은 [제작 가이드](content-guidelines.md)를 따른다.

## 실행 구조

시작 노드에서 제작 개수를 정한다. 서버가 최근 3일 게시물 성과를 한 번 갱신한 뒤 콘텐츠별 분석·제작을 병렬 실행한다. 기본 개수는 1개다.

각 작업은 분석·방향을 저장한 다음 콘텐츠 제작으로 이동한다. 서버가 출력과 저장 결과를 검사하며, 제작 완료에는 최신 저장본의 모든 슬라이드 미리보기 확인이 필요하다. CLI는 작업 전용 MCP로 자신의 draft와 프로젝트만 수정한다.

완성 포스트는 편집기에서 수정·내보내기한다. 실제 게시 URL을 등록하면 Apify로 게시 시각·성과·전체 슬라이드 축소본을 저장한다. 대시보드 달력도 이 기록을 사용한다.

## 화면과 제어

- 대시보드는 가장 왼쪽 고정 아이콘 탭, 제작 캔버스는 항상 유지되는 고정 탭이다.
- 시작 버튼은 캔버스의 시작 노드 안에 있다. Apify 미연결이면 오류를 표시하고 시작을 차단한다.
- 콘텐츠마다 색상이 다르며 진행된 단계가 순서대로 나타난다. 노드를 누르면 단계별 draft를 읽는다.
- DB 저장 시 노드 안의 저장 표시가 박동한다. 진행 중에는 시점을 자동으로 움직이지 않는다.
- 각 단계에서 아이콘 하나로 중단·재개한다. 캔버스 하단에는 전체 중단·시작 위치 이동·전체 보기 버튼을 둔다.
- 작업 삭제는 모든 단계 draft를 제거한다. 완성 포스트 삭제는 저장 프로젝트와 사용 이미지도 삭제한다.
- 제작 기록과 선별 레퍼런스는 오른쪽 패널에서, 제작 모델은 왼쪽 하단에서 확인한다.

## 저장소 정리

DB v15는 구형 템플릿 테이블·자산·연결과 프로젝트의 수동 게시 시각을 사용하지 않는다. 게시 상태의 기준은 제작 로그의 URL과 실제 게시 시각이다. 기존 게시글과 사용 이미지는 독립적으로 보존한다.

프로젝트와 draft가 없고 분석·방향·내용·게시 정보도 없는 빈 로그는 제거한다. 내용이 있는 로그와 게시 당시 이미지는 보존한다. 구형 DB 자동 변환과 영구 마이그레이션 도구는 제공하지 않는다.

자동 제작은 실제 게시글과 레퍼런스 이미지를 참고해 새 프로젝트를 만든다. 별도 고정 템플릿과 공통 시각 언어 편집 기능은 없다. `clone_project`는 사용자가 지정한 게시글을 독립적으로 복사하는 수동 기능이다.

## 검증 범위

단계 순서·출력 검증, 중단·재개·삭제, 중복 비교, 저장 실패 복구, URL 연결과 성과 수집, 게시 달력, 이미지 저장을 자동 검사한다. API/MCP 통합 검사와 격리 빌드도 수행한다.

검증용 DB·수집 응답으로 통과한 결과는 실제 모델의 콘텐츠 품질이나 실제 플랫폼 수집 성공을 뜻하지 않는다. 실제 제작 전에는 기존 게시 URL과 선별 레퍼런스를 보완하고 콘텐츠 1개로 전체 흐름을 확인한다.
